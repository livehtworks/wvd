# 王城阶段停顿排查

## 范围与结论

用户反馈王城等待过久。本次只读candidate64正式批次`1ADE8F5C-EBC0-4B3B-8987-82327F5F1ECB`第2至5轮的`result.json`、`action-timing.jsonl`，并对照实际调用链；排除包含冷启动和下载的第1轮。没有运行测试，没有停止循环，没有修改生产代码或配置。

第2至5轮均Completed，总耗时分别275.66、269.76、271.31、271.40秒。不是循环停止，但正常流程有可见的计算和固定等待开销。主线程互斥计时与worker耗时不能相加；以下不把游戏动画、网络响应和识别计算混称为网络延迟。

## 实际在做什么

每轮先查上轮遗留报告，退出公会，进入荒屋跳轮，再打开悬赏页刷新，最后离城。返城后另有提交报告、退出公会及住宿链。前置查遗留报告在每次重新prepare的Run均执行，不仅首次启动执行。因此前一轮已交完、已经住宿，下一轮仍会再进一次公会检查。

| 第2至5轮均值 | 出发前城市链 | 返城交报告与住宿 |
| --- | ---: | ---: |
| Session墙钟 | 90.86秒 | 62.19秒 |
| 主线程模板匹配 | 36.01秒 | 33.67秒 |
| 主线程等待并行识别 | 16.08秒 | 5.76秒 |
| 截图元数据查询 | 10.01秒 | 8.26秒 |
| 显式等待/轮询休眠 | 19.40秒 | 5.24秒 |
| 纯像素获取 | 1.30秒 | 1.25秒 |

两段合计约153秒、2428次实际模板匹配。它们包含公会、荒屋、轮盘、旅店及转场，不是全程站在同一张王城图上。输入校验、像素转换和其余调度另计，表中未列项不应归入截图。

## 已定位原因

### 1. 已确认跳轮成功后仍固定等10秒

`native/games/wvd/tasks/bounty_cycle.cpp`中`Leaped`业务确认后调用`delay_after("Leaped", 10000)`。第5轮该节点耗时10.339秒，其中显式等待9.892秒、实际模板匹配0次。这段不是识别不到，更不是网络错误。

来源是旧`src/script.py`蝎女分支中`CursedWheelTimeLeap()`之后的`Sleep(10)`，迁移时保留了固定等待。当前子流程已经确认跳轮后场景，仍叠加旧等待。修复应以目标页面可操作及覆盖层消失驱动后续，不用减少异常恢复期限来提速。

### 2. 城市确认间接执行无关剧情选项匹配

调用链：

`leave_bounty_board()` → `city = 郊外入口存在 AND NOT(剧情/公会菜单/列表/展示卡)` → `ordinary_story_page()` → `AUTO控件 AND 继续箭头 AND NOT(default_dialogue)`。

`native_recognizers.cpp`的`all/any`先求出全部子项，再合并布尔结果。因此即使AUTO和继续箭头不命中，仍调用`default_dialogue`。该模式先按序匹配`dialogueChoices`下14个旧英文选项；无选项命中才返回NoHit。候选都是不带ROI的模板请求。王城正常帧也因此执行原本仅在选项页才有意义的识别。

注意：没有选项命中时已不会继续扫整份启动guard，不能把全部成本都归因于启动候选；14项内部亦是首命中停止，问题是外层无门控地进入它。

第5轮退出公会的`Task_LeaveInspectedBoard_GuildLeave@await`：3次截图、84次实际模板匹配，总4.874秒；其中匹配3.380秒、等待并行识别0.497秒、元数据0.659秒，纯取图0.039秒。已有81次叶缓存命中，不能描述为“完全没有缓存”，但仍有大量实际计算。

### 3. 子流程结束后父级继续重复宽场景确认

同一轮退出公会确认后，父级`Task_LeaveBoard`仍用一张新帧执行52次匹配，耗时2.654秒。父级`Start`的场景条件包含城市/旅店/公会/郊外，以及blocking_screen、战斗和宝箱反证。

跳轮输入回执确认后，父级`Task_Leap`选路段又耗时6.154秒（5帧、113次匹配），随后才进入固定10秒的`Task_Leaped`。这是父级选择和确认阶段的耗时，不是发出了第二次跳轮。`Return`会使旧观察失效，新鲜度要求本身合理，但业务端重复大组合增加了成本。

`city.any`还由8种建筑入口组成；当前`any`不短路，所以命中一个建筑仍算余下候选。`time_leap.cpp`的跳轮后置又组合王城背景、任意城市、迷宫、小地图和返回按钮等，造成同一结果的宽场景确认。

### 4. ADB元数据开销，不是PNG解码慢

`devices/device_session.cpp`中截图元数据缓存超过1000毫秒或尺寸改变时，会分别查询`dumpsys window`与`dumpsys input`。识别本身超过1秒后，下一帧常再次触发查询。两个城市段的这部分平均18.27秒，而纯像素获取仅约2.55秒。

这不能通过删除前台包名/视口门禁解决；应研究合并传输、同连接代次缓存及失效条件，输入前的安全复核仍需保留。

## 修复优先级与边界

1. 消除跳轮后的固定10秒，用已确认目标状态和新帧可操作检查继续。
2. 普通剧情采用便宜的特征门控，仅在剧情控件确证后判断选项；城市正常路径不扫描14张无关旧英文选项。
3. 收窄父子业务后置，优先确认当前允许到达的场景。资源/参数完整性在发布及预检阶段验证，运行中仍传播实际执行条件的Error；不能直接把全部`all/any`改成短路而悄悄改变错误及输入授权语义。
4. 连续成功轮使用已确认“报告清空、住宿完成”的业务事实避免重复初始化巡查；冷启动、重启、未知现场仍检查遗留报告。不能无条件删除检查，否则会丢失中断恢复能力。
5. 最后优化截图元数据查询，不改变焦点、设备代次和视口安全边界。

固定等待和组合条件求值过量此前已在`action-timing-20260927.md`列为未实施优化候选。此次日志设置部署并未包含这些性能修改，不能将它们描述成已经修复。

当前日志能证明节点级实际开销及调用链，尚未逐个模板分摊每毫秒成本；也不能仅用不同时间运行的候选均值差证明Debug日志造成性能回退。本次保持候选不变，继续原50轮采集。
