# 流程检查分组与异常分派

## 本轮范围

按用户要求修正“正常流程反复全量检查、异常反而直接停止”的通用接线。修改 Windows Next 源码，不修改旧 Python 入口、用户配置、素材、运行数据或设备状态。用户要求提交后交给 GPT 讨论，因此不启动游戏循环、不替换正在使用的候选 EXE、不打包。

本轮仅证明下述源码接线和执行器行为，不宣称新代码已经通过实机或速度改善。此前候选的一轮成功与 33.68 秒技能记录属于此前构建，不能转记为本轮证据。

## 原问题

- `PipelineCompiler::compile_interruption()` 曾给正常识别、输入场景、业务确认包裹 `!blocking_screen`，给输入后置加入整个阻塞页条件，并将 Interrupt 放在后继最前面。
- `blocking_screen` 混合网络、下载、标题、Pause、死亡、加护、伏击和对话。正常战斗也需要证明这些页面不存在。
- 同帧缓存只减少重复叶子匹配；新帧仍重新匹配。正常技能阶段不需要这样全量否定其他场景。
- `RequireRecovery` 在原生图中是 Fail；名称本身不表示已经执行恢复。输入结果未确认又会禁止协调器自动重启，容易留下“发现异常却直接退出”的断点。

## 新的职责与顺序

| 组 | 入口 | 正常检查范围 |
| --- | --- | --- |
| 战斗 `combat` | 战斗 Definition | 行动人物、已选技能、详情、等级、目标、执行结果及战斗结束交接 |
| 宝箱 `chest` | 宝箱 Definition | 打开、选人、拆锁、奖励继续、返回迷宫或交接战斗 |
| 异常 `exception` | 当前结果连续未确认或等待预算到限 | 网络/下载/启动提示、Pause、死亡等已知异常 |
| 特殊 `special` | 异常组未命中后 | 已知选项、普通剧情、加护、伏击等特殊插入 |

正常业务候选先判断；不能因为异常处理器存在就在每一步抢先扫描。战斗结束、宝箱转战斗等正常交接仍由原业务图负责，不在所有帧全局扫描所有任务。

同一阶段连续 1 秒未确认后才启用异常诊断，其后普通诊断至多每秒一次；该间隔只是动画/加载去抖和扫描节奏，不是点击必须 1 秒生效的期限。业务原等待预算、输入证据 TTL 和 Run 总期限没有被此间隔缩短。预算耗尽前还有一次强制诊断。

诊断组按异常→特殊→作用域遭遇事件执行。异常组内部：网络处理器优先级 1000，其余已知异常 800；特殊页面 400。已命中高优先级时不扫描低优先级；同优先级仍检查歧义。单帧 NoHit 只等待，不直接判故障或重启。

作者显式声明的 `overlay` 抢占契约仍有效，不被静默改写成事后检查。内置自动添加的网络规则已改为 `exception`，包括输入的 `@await`。发布包装还把外层正向 `blocking_screen` 观察归到结果不符后的候选，避免只优化技能而保留外层 Blocked 抢占。

## 真正进入异常之后

1. 记录来源步骤、业务组、未确认原因、已检查组和选中事件。
2. 已知网络进入原重试处理器；其他已知异常或特殊页面进入现有 Common 处理器。仍用唯一 FlowExecutor 调用/事件栈，没有第二个执行器或后台循环。
3. 挂起当前调用和输入回执，事件处理时间按原规则记账。处理器禁止递归继承这些默认诊断规则。
4. 处理结束后用新帧重新核对原业务条件；处理器返回不等于技能/付款/报告已成功，不跳回任务入口、不重发已发送输入。
5. 没有已知事件时按原业务预算继续等待；预算耗尽、识别 Error、外部阻断或送达未知时保留诊断并明确退出，不能盲点、盲重启或假报成功。

本地 Interrupt/OutcomeBlocked 出口保留为明确转交，但只在正常候选全未命中、且处理器未接住时检查。不会在正常动作的前置/后置条件中全量扫描。Common 的 Resume 另排除战斗、迷宫和地图背景，避免把地图常驻继续导航按钮误作启动提示。

## 层次与证据

- `workflow/`：schema 5，保存业务检查组、异常候选标记及 Exception/Special 事件类别；序列化与校验同步更新。
- `runtime/`：拥有正常推进、无进展诊断、优先级、事件挂起、回执及恢复后的重新观察，不解释 WVD 素材。
- `games/wvd/vision/`：独立异常与特殊页面探针表，按序命中后停止；仍区分 Hit/NoHit/Error。
- `games/wvd/recovery/`：在正式启动包装中注册处理器并禁止自递归；启动页继续使用自身完整启动链。
- `games/wvd/tasks/`：正常图不再被通用阻塞检查包裹；保留旧业务阶段、技能消费及宝箱交接。

检查命令：`cmake --build next/build --config Release --target wvd_native_games test_native_flow test_native_author --parallel 4`；执行 `test_native_flow.exe` 及 `test_native_author.exe --dispatch`。不运行旧矩阵、全任务验证、资源长测或真实任务。

执行器检查通过：正常结果以及去抖期内自行完成的短暂动画均零次异常/特殊探针；输入前场景持续未确认时，不因反复选中同一分支而永久跳过诊断，处理后仅发送一次输入；未确认输入进入高优先级处理器后恢复并完成，底层业务输入仍只有一次，低优先级不扫描；未知页面完成诊断后保留未决输入并报告 ExternalBlocked。既有调用、事件退出、停止回执测试未删除或禁用。原输入在途场景不再依赖“必须第 3 张截图遇网络”的偶然帧数，改为输入状态和一次网络事件。

生产编译器定向检查通过：真实战斗工厂的 Lv5 技能图，正常节点不含通用 blocking_screen 包装；蝎女迷宫图经正式启动包装和强类型编译，战斗/宝箱及 @await 使用事后诊断类别，调用闭包与作用域校验通过。使用最小配置验证接线，不是实际角色技能或完整游戏任务验收。

完整构建与检查日志在本地 `next/.local/logs/flow-dispatch-*20260926.log`；不提交临时二进制或用户现场数据。编译器发现孤立节点时现在同时报告具体节点名，未放宽可达性校验。

## 未闭合边界

- 本轮没有实机回归。异常随机弹出、透明覆盖层下旧锚点仍命中、角色切换和实际技能耗时，需要新候选上的有限现场检查，不能用以上离线接线结果代替。
- 通用包装及正向阻塞候选已拆开，但部分专用复合识别器仍主动调用 blocking_screen，个别任务的地点/跳轮确认也保留直接 `!blocking_screen`。没有删掉这些安全反证，更没有宣称整个工程所有旧扫描都清零；进一步替换需逐条核对其正面业务证据。
- 已发送但未确认的副作用仍禁止重放。若异常处理器内部确认物理冻结而父输入仍未决，协调器仍可能按现有安全规则退出；本轮没有新增“丢弃未决回执后自动重启”的语义。这里是恢复链尚待讨论的边界，不冒称所有异常均可自动恢复。
- 未知维护、未知选项、素材缺失或识别错误不自动点击确认；已有生命周期恢复授权和边界不扩大。历史内存未归因问题仍未闭合。
