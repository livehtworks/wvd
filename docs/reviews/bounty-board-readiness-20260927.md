# 悬赏页误放行与返回链修复

## 问题与证据边界

用户现场观察到王城停留过久、进入委托后没有确认悬赏列表就退出跳轮。已停下连续循环，保留原日志，没有重启游戏、模拟器或更改 VPN。

- candidate19 实例 `DA080D3A-29DC-4290-8954-74C83DE902AD` 的 run 3：公会点击、委托点击之后，直接经过 `guild-open-bounties/Ready`、`Task_NoOldReport`，随后密集 BACK；没有悬赏页签输入。
- 原发布图确认 Ready 仅识别“懸賞令列表”标题，NoOldReport 仅追加当前帧没有报告按钮。没有已加载卡片或选中页签的证据。标题出现不证明列表内容已经加载。
- 原 LeaveBoard/Back 的后置条件包含输入前原菜单，所以同一页面可以被当作“返回成功”，产生约 0.3 秒间隔的连续 BACK。这是明确代码错误。
- 实机 run 4 从稳定“委託清單”运行公共切页，确实点击 `(692,1411)` 进入悬赏列表；该稳定委托帧的旧悬赏标题匹配只有 0.247。run 6 从王城进入公会后，游戏直接恢复上次选中的悬赏页，未点击页签但最终确为悬赏列表。因此“没有页签点击”本身不是充分故障证据。
- run 3 的历史截图每 15 秒保留一张，没有记录其约 6 秒时的精确决策帧。当前可以证实缺少加载确认与返回误判，不能将过渡帧竞争写成已经逐帧证明的唯一原因，更不能宣称每次未点击页签都是识别错误。

本地原始证据在 `next/.local/c11-flow-product`：`bounty-entry-repro.png`、`bounty-open-result.png`、`bounty-transition-035816/`；旧结果位于 `data/runs/<上述实例>/3/`。这些原始画面不公开上传。

## 修复契约

1. 繁中 `guild.bounties.page` 同时要求列表标题、选中悬赏页签和通用 WANTED 卡片，并反证委托标题。卡片不包含怪物名、奖励值或怪物头像，排序改变不影响页面识别。
2. 有报告立即提交。无报告须在已加载悬赏页上跨新帧再确认一次；一秒是负证据复核间隔，不是点击生效期限。未进入悬赏页、黑屏、过渡页都不能据此进入跳轮。
3. 开轮前检查、提交和刷新复用公共开页链。悬赏展示卡是可选的多页插曲：关闭后重新确认完整列表，不能把展示卡当成列表就绪。
4. 只有实际达成报告按钮才触发提交；必须见到已领取回执，关闭回执并回到已加载列表，才记账。报告提交不设置十秒独立短期限，不重复未知是否送达的提交。
5. 返回链单独封装并复用：识别列表“返回”后等公会菜单；识别公会“離開”后等城市。原页还在时不能判成功，安全菜单点击可以间隔重试。
6. 可选展示卡也可能在列表已经出现、返回输入已发送后才到达。返回等待允许将它交给关闭分支，但不能因此认定已退出公会。没有展示卡时直接按实际列表/菜单推进，不等待卡片出现。

源码在 `next/native/games/wvd/tasks/bounty_visit.cpp`、`bounty_cycle.cpp` 与语义目录、公共作者流程。英文既有提交链保留，不将繁中现场结果外推为英文实测。
