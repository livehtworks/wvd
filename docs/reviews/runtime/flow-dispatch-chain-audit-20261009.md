## 已确认的问题

### 1. 未执行节点失去条件后，返回重选的能力不一致

`runtime/flow_executor.cpp:531–539`只为Input、Observe及带guard的Route保存选择来源，而且要求多候选或返回目标列表。BusinessConfirm、RegisteredOperation及尚未进入的Call没有相同承接。

`execute_step`的guard NoHit路径（1050–1062）也只让Input/Observe/Route重选；业务确认即使尚未改变任何业务状态，也只等待原条件。其结果是“曾经选中”被当作必须等回来的页面，而不是需要重新确认的临时候选。

**实际影响不止战斗。** 宝箱Begin/Done、目标战结果、悬赏阶段完成、旅店付款/住宿确认都使用相同业务确认机制。不能因这些模块此前跑通过就排除同类竞态；本轮不声称每处都已实际发生故障。

### 2. 业务条件失效和操作等待混在一起

`flow_executor.cpp:1037–1048`的business_guard返回Waiting直接等待50ms，不返回原候选，也不走普通异常检查（仅可能处理Overlay）。

`games/wvd/native_operations.cpp:124–130`在确认条件NoHit、业务状态尚未改变时返回Waiting；执行器1273–1288将它与“操作已开始、还没完成”统一处理。不能仅给所有Waiting加重选，否则可能重做已经开始的操作。必须区分未开始、已提交、进行中和已完成。

### 3. 所谓异常检查并不检查正常业务分支

`runtime/flow_executor_events.cpp:79–105`的check_unexpected检查已注册的Exception/Special/Encounter事件；战斗正常角色、战后迷宫等同层候选不在其中。没有事件命中，不等于没有其它正常业务分支。

该函数一进入就设置exception_since，先于事件扫描节流。guard NoHit路径又先调用它、再尝试有限重选。因此正常动画、条件过期也能启动持续异常计时。50ms是等待唤醒间隔，不证明每50ms取得了新截图；应依据帧身份判断。

### 4. 超时前的正常复查同样漏掉节点类型

`flow_executor.cpp:358–379`到60秒会抓新图复查，但`recheck_normal_observation`（932–1019）只承接Observe/Poll；已经进入节点时仅查当前节点，未回原候选。扫描后继时遇到其它节点类型就中断。

`reclassify_timeout`（282起）又只覆盖Observe/Route/Poll/Wait和已声明的可达known_scene；过期Poll复查也限制候选类型。这些恢复入口的覆盖范围彼此不一致。BusinessConfirm在本次路径中连续漏过，最终“拿到了正常战斗截图，却仍按异常重启”。

`route_error`（270起）在异常计时有效时，会将部分阶段/等待/命中次数错误留在等待中，早于普通失败边分派。它不是完整正常场景重分类，不能指望失败边自动补救。

### 5. 已发送输入及事件返回也存在旧页面依赖

AwaitResult会检查声明的后置、异常事件及允许的同页重试；如果实际合法结果未进入后置/交接声明，就可能一直等原结果。事件处理成功后，resume_event仍依赖原resume_guard或父输入后置；页面已推进到另一正常阶段时，需要明确的局部恢复出口。

这里不能采取“没命中就丢弃输入、直接点下一分支”：送达未知或效果未确认必须保留。应先只读识别其它合法结果，核对原动作的实际结果，再决定继续、按已授权语义重做或交回业务重新规划。金币住宿可按用户许可重做；宝石购买禁令和未知输入保护保持不变。

### 6. 设备恢复与业务续接之间仍有断点

运行时60秒重启与协调器生命周期恢复是不同入口，不能仅审查run_builder的恢复原因白名单就推断普通NoHit绝不会触发重启。

`tasks/dungeon_route.cpp:205–230`区分目标战身份已授权、迷宫中重新定位、战斗中身份未知。最后一种明确RequireRecovery；当前恢复策略未承接该原因，所以重新进游戏后停止。不能把任意新战斗记成目标已击杀，也不能把成功启动游戏当作整轮恢复成功。

后续必须为任务明确：哪些已保留目标事实加新敌人证据可恢复；不能确认时，能否安全返回/重做本轮。不得通过伪造目标完成或清空未确认副作用来消除停止。

## 节点处理原则

| 情况 | 当前缺口 | 应采用的统一语义 |
| --- | --- | --- |
| 候选NoHit，尚未进入 | select_next能继续其它候选 | 保留，同一新鲜观察周期内按业务优先级判断 |
| 已选中但未执行，guard失效 | 按节点类型决定，部分死等 | 保留原局部候选上下文，重新选路；不跨任意阶段 |
| 业务条件已失效 | Waiting不区分原因 | 重新判断业务阶段，不把逻辑false当加载 |
| 业务确认尚未写入 | NoHit也按操作等待 | 安全退回当前业务分派，不记完成、不重复消耗次数 |
| 操作已经开始/输入已发送 | 仅原结果和异常事件 | 先只读核对合法结果，再依送达和效果决定后续 |
| 正常动画/加载/移动 | 可能启动异常计时 | 已知正常等待；同页无进展与正常推进分别记录 |
| 当前业务候选均不成立 | 异常与正常选路脱节 | 检查该范围异常、特殊事件，保留明确恢复入口 |
| 持续真实未知/不可恢复 | 60秒复查漏类型 | 用同一正常分类逻辑复核，仍异常才按既定60秒重启 |
| 识别Error/截图不可用 | 不应与NoHit混淆 | 保留错误详情；资源契约错误阻断，读取故障走设备恢复 |
| 恢复后页面变化 | 原resume_guard可能等不到 | 恢复到任务声明的业务观察入口，不盲回旧点击 |

不把整张流程图每帧穷举，也不让正常战斗每帧重查宝箱、公会、旅店。只在当前业务范围选路；该范围失效或出现异常证据时扩大到明确声明的恢复范围。

## 旧代码对照

`src/script.py:3395–3396`在StateCombat返回后将dungState置None，外层再进入IdentifyState。关键是每次战斗处理后重新确认当前场景，不把上一次场景永久锁住。

新版拆成更细的子流程和节点，却没有在所有“候选条件过期”“子流程返回后页面变化”处保留等价观察入口。应恢复这一语义，不复制旧英文模板、固定坐标或Auto兜底。

## 修复顺序与验收边界

1. 先统一未执行选路上下文及操作状态契约。覆盖业务确认、守卫、尚未调用的子流程，保留原期限和已确认进度；禁止反复重选就重置预算造成死循环。
2. 正常业务重选优先于未知异常计时。让执行前失效、操作前NoHit、超时前复查使用同一范围和同一规则，不再靠几份节点类型白名单分别修补。
3. 补输入后结果交接和事件返回恢复；逐项核对战斗、宝箱、导航、跳轮、悬赏、住宿，不改变已有副作用保护与业务成功条件。
4. 接齐重启后的目标业务续接规则，区分设备可用、游戏就绪、目标身份和整轮业务完成。
5. 在分支选择、条件失效、重选、等待原因变化、异常升级时记录节点/候选顺序/帧身份/语言与配方/结果及分数或证据/ROI/待确认输入/恢复去向。按状态变化和已有日志开关记录，不每次轮询写全量图与对象。
6. 针对上述真实失效路径做有限验收：未执行确认条件过期能回战斗；有输入不能重放；合法新页面可交回；真实未知才进入60秒恢复；恢复后不虚报目标完成。最终实机验证须另获继续运行指令，本轮保持停止。

已有selection-race主要覆盖Observe，不证明BusinessConfirm等价覆盖；历史大量通过不能替代上述验收。本轮没有执行这些验证，也没有宣称修复完成。
