## 直接机制与真实调用链

### 运行发布副本累积

任务准备沿既有Application → NativePublisher → Coordinator接管链进行，没有发现需要另加外部执行器的理由。

在本次源码基线`205692c`中，[native_publisher.cpp](../../../next/native/games/wvd/tasks/native_publisher.cpp)先执行`published_manifest = base_manifest`，之后遍历该清单发布资源：非ONNX成员通过`copy_member`复制；ONNX优先链接内容对象，系统真实链接容量耗尽时复制。请求接受后保留其发布目录；接管前失败撤回本次目录的所有权修复，不承担已结束历史的归档回收。

因此，“单次冻结正确、失败回滚正确”并不能阻止已接管发布长期累积。抽查一份repeat目录有600个文件，约136.31 MiB逻辑大小。1,334份完整资源树足以形成当前约79万个路径；同样的运行方式继续执行仍会增长。缺少已落实的历史引用退出与保留策略，是长期增长问题，不能靠重启服务或换请求ID解决。

前次T0新增的硬链接容量处理只解决了特定发布失败路径。容量耗尽后的复制会产生独立字节，不能被当成历史存储治理；也不能把这次事故处理成删除共享模型来绕过上限。

### 测试与候选收尾缺失

[submission_store_contract.hpp](../../../next/tests/native/submission_store_contract.hpp)为证明真实65,536条持久化边界，实际创建65,535份记录，写入第65,536份并拒绝第65,537份。这项核心边界验证有必要，不能用伪造计数或删测试代替。

问题在于多次隔离验收结束后，原始失败、最终回执、必要复现材料和可重建大夹具继续整体并列保留；三轮目录累计215,932个文件，没有完成收尾验收。不同失败需要修复并重验，不意味着每轮整棵夹具树都必须永久留存。当前统计证明留存规模，不声称每一次重验本身均无必要。

候选打包也保留了大量previous与staging。106个previous/staging中71个没有当前要求的有效交付标记头，已影响默认发布目标的准入。每次复制前检查剩余空间、为事务留余量，是单次安全措施；它不等同于跨批次、跨修复的总量预算和历史收尾。
