# WVD Next 新旧运行链事故审计报告

日期：2026-09-22  
结论：**当前 WVD Next 真实任务链不可交付，禁止继续实机运行。**

## 1. 事故定性

这不是“网络偶发延迟”或“某张启动图没识别到”，而是新版运行模型把三个不同阶段错误地合并成了一次同步事务：

1. 根据当前画面授权一次输入；
2. 等待界面产生变化；
3. 确认最终页面或业务终点。

手游中的点击只能证明输入已经提交。网络、动画、下载、服务器排队、弹窗和中间页面都可能使页面在数秒甚至更久后才变化。输入成功不等于页面已经跳转，更不等于业务已经完成。新版共用 `GuardedAction` 却要求一次动作在很短的后置预算内识别到预设结果，否则抛错并进入恢复链。这一语义会系统性破坏启动、地图、战斗、旅店、任务、对话和奖励流程。

## 2. “2 秒”实际是什么

`next/native/app/application.cpp` 将 `InputPolicy.max_frame_age` 固定为 `2000ms`。`next/native/devices/input_gate.cpp` 的 `same_frame()` 使用截图的 `captured_at` 到当前时间计算帧龄，并把该判断同时用于：

- 点击前场景授权；
- 底层输入许可；
- 点击后的页面确认；
- 普通业务观察确认。

这个值最多只能用于限制“点击前用于授权的画面是否仍然新鲜”。它不能用于衡量网络是否在两秒内响应，也不能用于判断点击后的识别结果是否有效。

当前实现还有两个放大因素：

- `AdbBackend` 在截图开始时记录时间，截图、前台查询和识别耗时都会消耗这 2 秒；
- 输入前 `context_matches()` 还会进行一次完整截图式上下文复核，进一步消耗帧龄。

因此，即使设备没有卡顿、网络没有异常，只要截图和识别本身超过两秒，有效证据也会被程序自行判为过期。

## 3. 已有真实证据

最后一次真实运行记录保存在 `%LOCALAPPDATA%\WvdNext\runs\<instance>\1`。事件链证明：

- VPN 检查和游戏启动成功；
- 正确识别到繁体中文免责声明 `boot_attention_zh`；
- 点击输入 `attempted=1`、`accepted=1`、`backend_called=1`，底层已经执行；
- 点击后的新帧仍能正确识别该页面；
- 从截图时间到提交识别结果共 `4253ms`；
- 因超过 `2000ms`，`confirm_scene()` 抛出 `SCENE_UNCONFIRMED`；
- 链路随后失败，而不是继续观察下一帧。

所以这次失败不是“没点到”，而是**点击已经发出、识别也成功，程序仍用错误的两秒规则否定了结果**。

## 4. 旧版实际采用的语义

旧版 `src/script.py` 虽然实现粗糙，但关键运行语义是异步、持续观察：

- `Press()` 只负责发送点击，不要求最终页面在本次调用内完成；
- `FindCoordsOrElseExecuteFallbackAndWait()` 会重新截图、识别、处理常见阻挡、执行一次动作、等待后再次观察；
- `WaitGameBootReady()` 使用独立的总预算循环处理标题、下载、弹窗和中间页面；
- 世界地图、时间跳跃和副本入口均通过多轮“观察 -> 单步输入 -> 再观察”推进；
- 应用恢复先尝试重启游戏，失败后才进入 ADB 或模拟器恢复；
- 蝎女任务从当前城市状态出发，先进入因果轮，再选择章节、任务并继续后续链路。

旧版的问题主要是识别和恢复策略过于粗暴，而不是要求一次点击同步完成整个页面跳转。新版没有保留这条最基本的业务语义。

## 5. 新版共用动作执行器的系统性问题

### 5.1 输入、转场和业务完成耦合

`next/native/runtime/guarded_action.cpp` 在发送输入后立即循环截图和识别后置条件，命中后再次调用 `confirm_scene()`。默认后置预算由 `PipelineCompiler` 设置为 `3000ms`。超时抛出 `POSTCONDITION_TIMEOUT`。

这意味着网络超过三秒、出现合法中间页、动画尚未结束或识别本身较慢，都会被当成动作失败。

### 5.2 后置结果错误复用输入时效

点击后的新帧虽然已经证明属于同一代次且晚于点击前帧，仍被 `same_frame()` 的两秒输入时效拒绝。业务 `confirm()` 也复用同一规则，导致“最终画面已看见，但识别耗时较长”仍可能失败。

### 5.3 默认错误出口过重

`PipelineCompiler` 给绝大多数节点默认设置 `on_error = RecoveryRequired`。普通转场等待超时不会回到状态观察器，而会直接结束当前会话并进入恢复判断。局部页面延迟因此被错误升级为全链恢复事件。

### 5.4 影响范围不是启动页一处

所有由 `click()`、`fixed_click()`、`swipe()`、`back()` 编译的动作都进入同一个 `GuardedAction`。当前任务和导航代码中此类调用约两百处，覆盖：

- 启动页、下载页和 Pause；
- 世界地图、城市和副本入口；
- 时间跳跃和因果选择；
- 战斗技能、目标和自动战斗；
- 旅店、补给、组队和恢复；
- 工会、任务对话、奖励领取和报告。

因此不能靠给启动页增加等待时间或放宽阈值解决。

## 6. 任务链和生命周期的其他断点

### 6.1 蝎女任务入口与旧版不等价

新版 `bounty_cycle.cpp` 的 `Start` 先要求当前已经处于因果轮/遗迹页面，成功后才调用 `time_leap_without_causality()`。用户从王城启动时，这个条件无法成立。

旧版会先从当前稳定场景进入因果轮，再选择章节和任务。新版把“进入因果轮”放在了只有进入因果轮之后才能到达的子流程里，形成入口倒置。

### 6.2 开始按钮不承接旧版自动连接

新版工作台在设备未连接时禁用“开始任务”，后端开始接口也直接要求已有 backend。旧版 `Farm()` 会先执行设备检查、必要的模拟器启动、ADB 连接和 VPN 处理。新版把这一完整启动链拆成了用户必须预先手动完成的连接步骤，界面和业务入口没有保持等价。

### 6.3 恢复会话可能在已断开的 backend 上执行

`InputGate` 析构会断开 backend。每个业务单元和恢复单元又建立独立 `ExecutionSession`。当前只对“初始生命周期计划”主动连接，而恢复计划不是初始计划，因此恢复单元可能在 backend 已被上一单元断开后直接执行停止/启动应用，导致恢复结构本身失败。

### 6.4 停止并不保证及时生效

停止请求能设置标记并请求会话停止，但 Maa/Controller 的同步等待仍可能阻塞。当前等待超时只记录 `STOP_TIMEOUT`，不会使底层阻塞调用真正返回。用户点击停止后界面可能继续处于停止中。

### 6.5 当前启动页补丁仍然错误

工作区中的 `progressed(current) = any(recognized, absent(current))` 不是有效修复：

- `recognized` 包含当前提示本身，所以页面完全未变化也可能被当作进展；
- 组合识别当前不会短路，仍可能扫描完整 `boot_post`，不能消除高识别耗时；
- 它继续使用 `GuardedAction` 的同步后置事务，没有解决根本模型。

该补丁必须视为未完成代码，不能据此恢复实机验证。

## 7. 正确的运行模型

### 7.1 输入阶段

输入阶段只做：

1. 捕获当前画面；
2. 识别并确认允许操作的场景和目标；
3. 记录动作意图；
4. 向底层提交一次输入；
5. 记录底层是否接受。

输入提交成功后立即撤销许可并返回，不等待最终页面。

### 7.2 转场观察阶段

独立观察节点在自己的总预算内循环：

- 到达目标页：进入下一业务节点；
- 仍在原页面且动作可安全重试：经过防抖后有限重试；
- 下载、联网、动画或已知中间页：等待并继续观察；
- 已知阻挡页：进入专用处理器；
- 未知页面：停止输入并保留诊断，不升级为模拟器重启。

网络等待预算必须属于具体转场或业务流程，不得复用截图帧龄。

### 7.3 不可逆动作

领取奖励、付款、提交任务、选择因果和其他不可逆动作必须在点击前记录 pending intent。点击后只观察：

- 明确目标状态出现才提交业务完成；
- 明确仍在原状态且业务允许时才有限重试；
- 结果不确定时停止并要求人工确认，禁止自动重放或重启。

### 7.4 时间边界分离

至少需要四类独立时间：

- 输入前画面授权有效期；
- 一次底层输入调用超时；
- 页面转场/联网等待总预算；
- 整个业务单元总预算。

截图应记录采集开始和采集完成时间。输入授权可依据采集完成时间和上下文复核；点击后的业务证据只要求同一运行代次、连接代次、动作 epoch 且确实晚于动作，不得再套输入前的两秒 TTL。

## 8. 必须按顺序完成的修复

1. 拆分 `GuardedAction`，建立“受控输入提交”和“独立状态观察”两个契约。
2. 将启动页改成状态分派循环，每轮最多处理一个已确认页面，然后回入口重新观察。
3. 修正帧时间模型，移除后置/业务确认对输入 TTL 的复用。
4. 用轻量设备、前台和 viewport 核对替代输入前第二次完整截图。
5. 修复恢复单元连接所有权，确保恢复操作前 backend 已连接。
6. 修复蝎女链，使其能从王城等稳定场景先进入因果轮。
7. 为不可逆动作加入 pending/confirmed/ambiguous 三态，禁止不确定重放。
8. 让底层等待可取消或有界返回，停止按钮必须最终进入静止状态。
9. 逐条迁移旧版真实业务入口语义，不能仅凭节点存在或离线测试宣布承接。

## 9. 后续验证限制

在上述结构修复完成前：

- 不启动 WVD Next 实机任务；
- 不重复跑启动矩阵、压力测试或全任务测试；
- 不打包或标记可交付；
- 不允许自动重启模拟器；
- 不以编译、Mock、离线图片或节点数量替代真实功能。

结构修复完成后，唯一允许的首次实机验证是最小可逆链：连接既定设备 -> 幂等检查 VPN -> 启动游戏 -> 处理多阶段启动页 -> 到达稳定王城画面 -> 用户停止。该链通过前不执行蝎女任务和任何资源消费操作。
