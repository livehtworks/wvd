# M4 Pause 有界恢复

## 行为与范围

固定旧源码 `Factory.IdentifyState` 连续六次点 `(450,760)`，每次等待两秒，仍检测到 Pause 后请求游戏恢复。新版把这条链写入既有 `recovery::boot_workflow` 的 Maa 节点，启动就绪和普通阻塞处理共用，不增加第二个轮询执行器。

- Pause 加入统一 `blocking_probes`，防止底层残留 dungeon/combat 图标让覆盖层被当成已就绪。
- 每次点击由当前帧 Pause 场景授权，后置必须是新帧中的已知状态；不以点击返回值或背景运动判定恢复。
- 最多连续六次；第六次后也先复核已恢复，仍 Pause 才给 `pause.physics_frozen`。恢复由原有 RunCoordinator 静止/新代次链负责，视觉代码不重启设备。
- 角色面板、恢复面板、技能详情及底部 Close 仍作为识别负例。所需图片由编译器收集进资源清单。
- 使用现有 M3 布局分支，没有把未迁移的 Tesseract 或真实 Pause 质量标为通过。比旧未知轮询提前观察覆盖层是明确改变，避免先执行底层动作。

## 当前验证

构建通过。首轮 4 方法中 2 通过、2 失败（71.904 秒，`m4-workflow-q4rgq7bn`）：后两项行为分别为六次点击后静止 Interrupted、一次点击后 UserStopped，均无错点；断言误把 Run 通用 reason 当 Session 具体 reason、误写停止枚举为 Cancelled。按已有 Run/Session 契约修正两项断言，不修改运行代码、不削弱输入次数或具体原因检查，保留首次证据并定点补验。

首次点击恢复、第六次恢复及四种面板负例通过。场景图片是标明的合成数据，只有预期输入推进状态，实际固定 Maa/OpenCV 和生产门禁执行。

后续还需普通阻塞和启动恢复回归；不操作当前游戏、不打包旧版、不放行生产。
